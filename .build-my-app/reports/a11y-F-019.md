## B. Findings

### Major
**M1. The slider announces the minimum when the selection's sizes differ.** (4.1.2 Name, Role, Value; 1.3.1.) StylePanel.tsx:393 and :398. With a multi-selection of differing widths (R7/AC10) `field.value` is null, so the slider gets `value={field.min}` and no `aria-valuetext`; a screen reader says "1" (or 1 px) while the field is empty. Not reproduced: my automated multi-select did not select both shapes, so confirm this by hand. Fix: when `field.value === null` do not render the slider (the field alone says "unset"), or render it `aria-disabled` with `aria-valuetext` set to a COPY string such as "Mixed sizes".

### Minor
**m1. No Home and End on the colour radio group.** (Advisory; ARIA APG radio group does not require them.) StylePanel.tsx:253-275. Home and End do nothing (focus stayed put in the run). Fix: Home focuses and picks the first option, End the last (End on an unused custom swatch only focuses it, as in R1). Optional.

**m2. The custom swatch gives no cue that it opens a dialog.** (4.1.2.) StylePanel.tsx:296-316. It is `role=radio`, so a screen reader says "radio, Custom color, 9 of 9". Enter, Space and click open the native picker; nothing says so. aria-haspopup is not allowed on radio (axe aria-allowed-attr). Fix: `aria-description` or `aria-describedby` pointing at an `sr-only` hint ("Opens the colour picker"), as a new COPY id. Needs a spec/copy decision.

**m3. Focus return after the picker closes depends on events some browsers do not fire.** (2.4.3 Focus Order; R9.) StylePanel.tsx:216-226 and :166. `backToText` runs only on `change` or `cancel`. Chromium closes without a choice with neither event (as in my run with the stubbed picker, the click path kept focus in the textarea because the swatch click does not take focus). The keyboard path (focus on the swatch, Enter, Esc or click away from the picker) can leave focus on the swatch while a text is still being edited, so typed characters go nowhere. Fix: also return focus on picker `blur` or `focusout` of the hidden input, or on window refocus after opening, when `textEditing` is set. Needs a manual check in Chrome, Firefox, Safari.

**m4. Clamped or rejected size gives no non-visual feedback.** (4.1.3 Status Messages, advisory.) StylePanel.tsx:350-358. 9999 becomes 100 and "abc" restores the old value; a screen reader user hears the new value only on re-reading the field. Fix: announce through the existing `tk-sr` live region ("Size set to 100 px (maximum)"), new COPY ids.

**m5. Size field and slider do not reach the touch-target size everywhere NFR-07 expects.** (2.5.8 passes at 24 px; NFR-07 is 44 px.) custom.css:49-56 and :64-68, :75-81. The 44 px `min-height` is only inside `@media (pointer: coarse)`. On the narrow layout at 600 px with a fine pointer the swatches are 44 px (container query) but the field is 28 px; on a coarse wide panel (tablet at 800 px or more) the slider stays 28 px high and its thumb is the browser default. Fix: also apply `min-height: var(--tk-size-touch-target)` to `.tk-size__input` in the narrow container query, and to `.tk-size__slider` in the coarse block.

**m6. Forced colours: focus and checked rings keep author colours.** (1.4.11, 2.4.7, forced-colors support.) custom.css:7-17 and :87-91; drawing.css:461. `.tk-swatch` has `forced-color-adjust: none`, so the checked ring is accent and the focus ring (custom.css:15-19) stays the accent token; only the checked state gets a `Highlight` outline. In my emulation (light tokens, forced) the checked swatch computed `border 2px rgb(104,55,224)` plus `outline Highlight`, and unchecked swatches kept the token border `rgb(140,130,162)`. Under a dark forced-colours theme these token colours sit on a system background the tokens were not designed for. Fix: in the `forced-colors` block set `.tk-swatch[role=radio]:focus-visible { outline-color: Highlight }` and `.tk-swatch--custom { color: CanvasText; border-color: CanvasText }` (the border and the unused-icon mark), while keeping the fill colours via `forced-color-adjust: none`. Visual confirmation is manual.

**m7. Size field has a fixed width and height, so text-only scaling can clip it.** (1.4.4 Resize Text.) custom.css:49-52: `width: var(--tk-size-field)` (56 px) and `height: var(--tk-size-control)` (28 px) at `font-size-lg` (17 px). Browser zoom is fine; OS or browser text-only scaling at 200 percent (34 px digits) will clip three-digit values (up to 400) and the browser's spin buttons overlap digits on hover. Same pattern as the existing position and size fields. Fix: `min-height` instead of `height`, `min-width` or `width: 4.5ch` with the digits plus the spinner. Check by hand.

**m8. The hidden colour input is `aria-hidden` yet takes focus in some browsers.** (4.1.2.) StylePanel.tsx:320. Firefox and Safari may focus the input when the picker opens, so a focused element is hidden from assistive technology; the native popup anchors at the 6 x 4 px `tk-sr` input, not at the swatch. Fix, if the manual pass shows it: drop `aria-hidden` and give the input `aria-label` with the same name as the swatch (it is out of the tab order anyway), or position it over the swatch. Manual check.

## C. Needs a manual pass (not automatable here)

2. Screen readers: VoiceOver (macOS, iOS), NVDA with Firefox and Chrome, TalkBack. Check: "radio, 9 of 9" with state, the custom name with hex, announcement after arrow pick, slider value text, the field's range, m1 to m4.
3. Windows High Contrast / forced colours with both dark and light themes (m6): are the checked, focus and unused custom swatches distinguishable.
4. Text-only zoom and OS font scaling at 200 percent (m7), and 400 percent browser zoom at 320 CSS px (checked at 320 px width only).
5. Touch: tapping each of the 9 swatches and the field on a real phone; slider drag (not offered on the narrow sheet) on a coarse wide tablet (m5).
6. Focus return after the picker closes during text editing, keyboard path (m3).
7. Switch and voice control: all actions have a keyboard or single-tap route (the slider has the field as a non-drag alternative, 2.5.7 met).
8. Real device check of the colour-only issue: the custom swatch's checked state is a border/ring plus a non-colour difference in thickness (2 px against 1 px with an inset gap), so 1.4.1 appears met; confirm with colour-blindness simulation.
