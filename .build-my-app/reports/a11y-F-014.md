# Accessibility audit: F-014 (Warn before losing work), commit 90b7c96

Method: static read of the diff e2053a3..90b7c96 plus the 12 screenshots. No accessibility-tree dump or screen reader was run. Contrast ratios were computed from the tokens in src/app/styles/tokens.gen.css. Line numbers are in the worktree.

## Findings

### M1 (major): Nothing is announced after Start over
- Where: src/app/clear.ts:19 (`endSession()`), src/app/state.ts:107-116.
- Criterion: WCAG 4.1.3 Status Messages, NFR-06.
- Problem: the canvas is replaced by the empty state and no `announcePolite` call is made. Loading announces `a11y.loaded` (loader.ts:47). Undo, delete and the other actions all announce. Focus returns to the More button, so a screen reader user hears nothing about the change.
- Fix: add a `COPY-a11y.cleared` string (en-US and vi-VN, for example "Started over. Drop, paste or open an image.") and call `announcePolite` after `endSession()`. The `role=status` region at Shell.tsx:164 sits inside `<main>`, which stays mounted in the empty state, so it works. If the toolbar buttons that are disabled in the empty state matter here, say that in the message too.

### M2 (major): The disabled Start over item is hidden from arrow navigation and from screen readers
- Where: src/app/MoreMenu.tsx:23 (`enabledItems` filters `!b.disabled`) and :149 (native `disabled`).
- Criterion: WCAG 4.1.2, 1.3.1, APG menu pattern.
- Problem: this applies when no image is loaded. A native `disabled` button is skipped by ArrowUp, ArrowDown, Home and End, and is often not reachable in browse mode. The user cannot learn that Start over exists. Tab closes the menu (:117), so that is not a workaround. With an image loaded there is no issue.
- Fix: use `aria-disabled="true"` with a guard in `onClick`, and keep the item in the arrow order. Alternatively, accept the omission and record it as a decision. If `aria-disabled` is used, `enabledItems` must stop filtering.

### m1 (minor): The focus-return fallback cannot work in the empty state
- Where: src/app/focus.ts:9-16 and src/app/Shell.tsx:126 (`tabIndex` is undefined when there is no image).
- Problem: today the opener is the More button, which stays in the DOM and is no longer inert, so focus returns correctly after both Cancel and Confirm. If the opener is ever gone, the fallback `.tk-work-area.focus()` does nothing. It has no `tabindex`, so focus is lost to `<body>`. The comment at focus.ts:3-5 promises otherwise.
- Fix: give `main` `tabIndex={-1}` when empty, or fall back to the More button.
- Manual check: confirm in a browser that, after Confirm, `document.activeElement` is the More button (the e2e in leave.spec.ts may already assert this).

### m2 (minor): The dialog's Tab trap only runs on keydown, and it also catches the Tab key when focus is already outside
- Where: src/app/ConfirmDialog.tsx:36-47.
- Problem: the trap is acceptable because the rest of the tool is `inert` and the handler is in the capture phase. Two small gaps remain. `items.length` is 2, so the trap works. The `i < 0` branch always sends focus to the first item, including on Shift+Tab, where the last item is expected.
- Fix: `i < 0 ? (e.shiftKey ? items.length - 1 : 0)`.

### m3 (minor): The same text appears as title, message action and menu item
- Where: ConfirmDialog.tsx:17.
- Problem: "Start over" is the menu item, the dialog action and, with "?", the title. This is fine. However, the destructive effect ("can't be undone") is stated only in the description. With `alertdialog` plus `aria-describedby` it is read on open, so this is acceptable.
- Fix: none needed. Verify manually that NVDA and VoiceOver read the title and message on open.

### m4 (minor): Danger styling is colour and border only
- Where: src/app/styles/components.css:59-62.
- Problem: the danger button is distinguished from Cancel by text and border colour. This is not a WCAG failure because the label carries the meaning. It is also less prominent than the primary action in forced-colors mode.
- Fix: none required.

## Passes (automated or static)

- Menu semantics: `role=menu` with an accessible name (MoreMenu.tsx:138), `role=menuitem` on the buttons, and `role=separator` between groups (:140). The separator is a non-focusable `div`, so it is skipped by arrow keys. Order is Download (narrow only), Keyboard shortcuts, separator, Start over.
- Keyboard: Up and Down wrap, Home and End go to the first and last enabled item, and Esc closes and focuses the button. `aria-haspopup`, `aria-expanded` and `aria-controls` are correct on the button.
- Dialog: `role=alertdialog`, `aria-modal=true`, labelled and described, with focus moving to Cancel (the safe choice) in a layout effect. The rest of the tool is `inert`. Esc cancels in the capture phase, and a click outside does nothing.
- Focus return after Cancel and after Confirm goes to the More button (opener captured at ConfirmDialog.tsx:33, restored through `returnFocusLater`). The menu closes before the dialog opens (MoreMenu.tsx:155), so the opener is the button, not the removed menu item.
- Contrast, computed (WCAG AA 4.5:1 for text, 3:1 for UI):
  - Danger text on surface: dark #FF8595 on #18121F is 7.9:1. Light #C0243B on #FFFFFF is 5.9:1.
  - Disabled item (muted): dark 6.25:1, light 6.92:1. Disabled text is exempt anyway.
  - Control borders (line-strong): dark 3.34:1, light 3.6:1.
  - Accent focus ring on surface: dark 5.99:1, light 6.54:1.
- Target size: menu items are `min-height` 44px unconditionally (export.css:76). Dialog buttons use the tool-button size and grow to 44px on a coarse pointer (components.css:289-295). Both exceed the 24px WCAG 2.2 minimum.
- vi-VN: "Bắt đầu lại", "Bắt đầu lại?" and the message are present in messages.gen.ts:202, 254 and 255. The dialog is 420px wide with `flex-wrap` on the actions, so longer Vietnamese text wraps rather than clips. Spacing and diacritics were not checked at 200% zoom.

## Needs a manual pass

1. Screen reader (NVDA/Firefox, VoiceOver/Safari, and TalkBack if used): the menu announcement, the disabled item, the `alertdialog` reading on open, and what is read after Confirm (see M1).
2. 200% text zoom and 320px reflow with vi-VN: dialog and menu wrapping.
3. Forced-colors and high-contrast modes: the danger button and the separator (the separator has no forced-colors rule, since its background is a custom colour; check that it remains visible).
4. Reduced motion: no new animation was added by this commit.
5. `lang="vi"` on the document when vi-VN is active (not verified in this diff).
6. Real touch device: menu item targets and the dialog's two buttons.
7. Focus visibility inside the menu in the screenshots: the focus ring was not visible in the static captures, so it could not be confirmed.
